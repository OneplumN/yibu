## 核验方法和限制

- 每项均核对了实际源码、调用入口及现有防护。
- 使用独立 fake-indexeddb 数据库、mock SQLite 和 mock 网络进行了 18 个隔离验证。
- 不读取或修改用户真实数据库、备份和密钥，不调用收费模型接口。
- 文件测试使用临时目录，检查 UTF-8、Unicode、CRLF 的真实本机读写。
- Windows、磁盘实际写满、进程崩溃、真实 SQLite 池事务、多窗口冲突和有效密钥请求未实测。
- 测试支持其具体结论，不把 mock 结果当作真实桌面端端到端验收。
- 本轮仅核验、记录；没有根据报告继续修改业务逻辑，也没有提交、推送或发布。

## 结论和处理顺序

不能采纳“3 个 P0、18 个缺陷”的统计。目前没有证据支持 SQL 注入 P0。
需要优先处理的是用户操作可触发的数据丢失，按 P1 处理：

1. 导入前深度校验，存储层原子替换，失败保留旧数据。
2. IndexedDB 和 SQLite 焦点列表替换的失败完整性。
3. 项目、焦点列表的并发写入和跨窗口冲突。

开发快照同步、数据库初始化与重置互斥随后处理。备份明文密钥是上一轮独立发现，
仍然开放。性能建议、未来迁移准备与可观测性不能与已复现的数据丢失混为一谈。

## 修复示例审核

- 递归 importSnapshot(backup) 不可靠：若仍然磁盘满或数据库不可写，恢复也失败；
  它不能提供进程中断后的保护。Promise.all 失败后其他写入还可能继续，恢复期间也会冲突。
  应优先通过一个存储事务原子替换；备份可以额外保护，但不能代替事务。
- 先 get(version) 再无条件写入不是原子乐观锁；两个写者可同时读到同版本。
  需要存储层原子条件更新，检查受影响行数；IndexedDB 需在同一事务内读、比较、写。
- Tauri SQL 插件使用连接池，不能未经验证就认为多次 execute("BEGIN"/写入/"COMMIT")
  一定属于同一事务连接。具体实现应验证连接绑定，或放到 Rust 的单事务命令中。
- IndexedDB 的同步 put 异常与异步请求错误要分别测试。捕获异常后只换错误文案不保证 abort。
- 模型 ID 不应强制转小写；ErrorBoundary 不替代异步 catch；文件 sleep 与哈希不替代原样校验。
- 原报告测试示例用了不存在的状态 "doing"，当前状态是 "in_progress"，不能直接运行。

## 分批上线建议核验

原第一批中，导入完整性与并发风险方向正确；项目删除需注明当前缺 UI 入口。
原第二批应把焦点列表替换的原子性提前，SQL 白名单不能以“现有 P0 漏洞”为理由阻塞发布。
原第三批的大规模性能、文件保存、边界处理应由复现结果驱动，不能为假设追加等待和重试。
原第四批的日志、错误恢复和迁移演进有价值，但 80% 覆盖率没有现成测量依据。

建议下一轮验收按数据完整性组织：导入失败旧数据不变；焦点替换失败旧列表不变；
并发改动不丢失；读写中的 reset 不悬挂；快照最新写入最终落盘且错误可见。
